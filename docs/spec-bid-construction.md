# 시공 입찰 및 계약 기능 명세서

> 기존 설계 입찰/계약 시스템 확장 · 작성일: 2026-03-10 · 상태: Draft

---

## 1. 도메인 개요

건축주가 **시공 입찰공고**를 등록하면 **시공사(건설업체)**가 견적 제안서를 제출하고, 선정 후 **표준도급계약 → 전자서명**으로 이어지는 구조.

```
시공 입찰공고 등록 → 견적 제안서 접수 → 업체 선정 → 도급계약 초안 → 전자서명 → 계약 체결
```

> **설계와의 관계:** 설계 계약이 체결된 공고에서 시공 입찰을 연계 등록할 수 있음 (설계도서 자동 첨부).
> 독립적으로 시공만 단독 등록도 가능.

---

## 2. 설계 대비 차이점 요약

| 구분 | 설계 | 시공 |
|------|------|------|
| 참여 주체 | 건축사 (architect) | 시공사 (contractor) |
| 분야 구분 | 가설계 / 본설계 | 신축 / 증축 / 리모델링 / 인테리어 |
| 스타일 단계 (4단계) | 디자인요소 + 외장재 + 레퍼런스 | **시공 요구사항** (공법, 자재, 공기) |
| 비용 필드 | 희망 설계비 (만원) | 희망 공사비 (만원) |
| 제안서 핵심 | 설계 소견 + 설계비 | **견적서 + 공사 소견 + 공사비** |
| 계약서 양식 | 건축설계 표준계약서 | **건설공사 표준도급계약서** |
| 계약서 핵심 테이블 | 기성 지불 일정 + 설계 도서 | **공정별 기성 일정 + 자재 내역 + 하자보증** |
| 인증 서류 | 토지소유, 건축가능, 건축허가 | 토지소유, 건축허가, **설계도서 확보** |

## 3. 데이터 모델 (설계와 공유하는 테이블 + 시공 전용 테이블)

### 3.1 공유 테이블 (변경 없음)

아래 테이블은 설계와 동일하게 사용. `bid_categories`에 `시공`이 추가되는 것으로 분기.

- `bids` — field 구분 없이 공유. `bid_categories`로 분야 판별
- `bid_categories` — `시공` 카테고리 행 추가
- `bid_restrictions` — 동일 구조 (지역, 업력, 포트폴리오 제한)
- `bid_invitations` — 동일 구조
- `bid_site` — 동일 구조
- `bid_building` — 동일 구조 (대지면적, 건축면적, 층수 등)
- `bid_certifications` — cert_type에 `설계도서확보` 추가
- `bid_likes` — 동일 구조
- `proposals` — 동일 구조 (fee 필드명을 `proposed_fee`로 통합)
- `proposal_attachments` — 동일 구조
- `contracts` — 동일 구조
- `contract_items` — key 목록만 다름
- `contract_item_histories` — 동일 구조
- `contract_attachments` — 동일 구조

### 3.2 bids 테이블 확장

## 4. 화면 명세

### 4.1 입찰공고 등록 — 시공 분야 (`/bids/new`)

5단계 위저드를 설계와 공유하되, **4단계만 시공 전용**으로 교체.

| 단계 | 이름 | 설계와 차이 |
|------|------|-------------|
| 1 | 사업 부지 설정 | **동일** |
| 2 | 입찰 정책 | 분야에서 `시공` 선택. 시공범위(신축/증축/리모델링/인테리어) 라디오 추가. 설계범위(가설계/본설계)는 숨김 |
| 3 | 건축 목적·규모 | 설계비 → **공사비**(min/max), **희망 공사기간**(개월) 추가 |
| 4 | **시공 요구사항** | 설계의 "건축 스타일" 대체. 아래 상세 |
| 5 | 공고 신뢰 인증 | 건축가능 → **설계도서확보** 인증 교체 |

### 4.2 입찰공고 상세 — 시공 분야 (`/bids/:id`)

설계 상세와 동일한 2단 레이아웃. 차이점:

| 섹션 | 설계 | 시공 |
|------|------|------|
| 요약 카드 | 설계비 범위 | **공사비 범위 + 희망 공사기간** |

| 인증 항목 | 건축가능 여부 | **설계도서 확보** |

## 5. 계약서 — 건설공사 표준도급계약서

### 5.1 계약서 양식 차이

설계는 `건축설계 표준계약서 (건축사법 제23조제1항)`를 사용하지만,
시공은 **`건설공사 표준도급계약서 (건설산업기본법 제22조)`**를 사용.

### 5.2 계약서 섹션 구성

| # | 섹션 | 편집 | 설계 계약과 비교 |
|---|------|:---:|---------------|
| 1 | 계약 당사자 | 읽기전용 | 갑: 건축주(도급인), 을: 시공사(수급인). 건축사→시공사 변경 |
| 2 | 공사 개요 | 읽기전용 | 건물명칭, 대지위치, 공사종류(신축/증축/…), 구조, 규모 |
| 3 | 계약 조건 | ✓ | **계약금액, 계약일, 착공일, 준공예정일, 공사기간, 지체상금율** |
| 4 | **공정별 기성 일정** | ✓ | 설계의 "기성 지불 일정" 대응. **공정명·기성율·금액·예정일** |
| 5 | **자재 내역** | ✓ | 설계의 "설계 도서" 대응. **자재명·규격·수량·단가·금액** |
| 6 | **하자보증** | ✓ | **신규**. 하자보증기간, 하자보증금율, 하자보증 방법 |
| 7 | 특약사항 | ✓ | 동일 (2,000자) |
| 8 | 첨부파일 | ✓ | 동일 + 견적서, 설계도서, 공정표 등 |
| 9 | UCanSign 안내 | 읽기전용 | 동일 |

### 5.3 contract_items 확장 (시공 전용 key)

기존 설계 계약의 공통 key는 유지하고, 시공 전용 key를 추가:

| key | 타입 | 설명 | 설계/시공 |
|-----|------|------|-----------|
| contractType | enum | 계약 유형 (`설계` / `시공` / `감리`) | 공통 (신규) |
| — 기존 공통 키 — | | buildingName, landLocation, constructionType, 면적, 당사자 정보 등 | 공통 |
| contractAmount | number | 계약금액 (원) | 공통 |

| **constructionStartDate** | date | **착공일** | 시공 전용 |

| **constructionDuration** | number | **공사기간 (일)** — 자동 계산 | 시공 전용 |

### 5.4 MaterialItem (자재 내역, JSON 배열)

`contract_items.key = 'materialList'`에 저장.

```typescript
interface MaterialItem {
  materialName: string;      // 자재명 (예: "레미콘 25-210-12")
  spec: string;              // 규격 (예: "25MPa")
  unit: string;              // 단위 (예: "m³", "ton", "EA")
  quantity: number;          // 수량
  unitPrice: number;         // 단가 (원)
  amount: number;            // 금액 (원) = quantity × unitPrice
  remark: string;            // 비고
}
```

### 5.5 DefectWarranty (하자보증, JSON 객체)

`contract_items.key = 'defectWarranty'`에 저장.

```typescript
interface DefectWarranty {
  warrantyPeriodYears: number;   // 하자보증기간 (년) — 기본 3년 (건축물 구조별 상이)
  warrantyRate: number;          // 하자보증금율 (%) — 기본 3%
  warrantyMethod: string;        // 하자보증 방법 (현금보증, 보증보험, 이행보증보험)
  warrantyStartCondition: string; // 기산일 ("준공검사 완료일", "사용승인일" 등)
  defectItems: DefectItem[];     // 하자보증 세부항목 (선택)
}

interface DefectItem {
  category: string;   // 공종 (예: "구조체", "방수", "미장", "도장")
  periodYears: number; // 보증기간 (년) — 공종별 상이
  remark: string;
}
```

### 6.2 계약 상세 (`/contracts/:id`)

설계 계약 상세와 동일한 2단 레이아웃 구조에서:
- **자재 내역 섹션** 추가 (설계 도서 대신)
- **하자보증 섹션** 추가
- 우측 카드에 **착공일, 준공예정일, 공사기간** 표시
- 타임라인 동일 (8단계)

### 6.3 계약 수정, 전자서명

설계와 동일한 플로우. 양식만 시공 계약서로 교체.

## 7. API 확장

### 7.1 기존 API 파라미터 확장

| API | 확장 내용 |
|-----|----------|
| `GET /api/bids` | query에 `construction_scope`, `construction_fee_min/max` 추가 |

### 7.2 계약 API

기존 계약 API 그대로 사용. `contract_items`의 key 목록만 확장되므로 API 변경 불필요.
`contractType` key로 계약 유형을 판별하여 프론트에서 적절한 양식을 렌더링.

## 8. 검증 규칙

| 규칙 | 설명 |
|------|------|
| 기성율 합계 100% | 설계와 동일 |
| 착공일 < 준공예정일 | 날짜 유효성 |
| 공사기간 자동 계산 | 준공예정일 - 착공일 (일) |
| 자재 금액 자동 계산 | 수량 × 단가 |
| 하자보증기간 ≥ 1년 | 최소 보증기간 |
| 지체상금율 0.01% ~ 1% | 범위 제한 |
| 견적서 첨부 필수 | 시공 제안서 제출 시 |

## 9. 설계→시공 연계 시나리오

```
1. 건축주가 설계 입찰을 등록하여 건축사를 선정하고, 설계 계약을 체결
2. 설계가 완료되면 (계약 체결 상태), 건축주가 시공 입찰을 등록
3. 시공 입찰 등록 시 "설계 계약 연결" 옵션:
   - 설계 계약 ID를 선택하면 → 설계도서가 자동 첨부
   - bid_construction_requirements.linked_contract_id에 저장
   - 시공 입찰 상세에 "설계사: OOO건축사사무소" 표시
4. 시공사가 설계도서를 확인하고 견적 제안서를 제출
```
